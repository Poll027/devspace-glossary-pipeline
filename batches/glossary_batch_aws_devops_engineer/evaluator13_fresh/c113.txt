tb1: A release security scan is useful as a gate only when its evidence is compared with an explicit severity threshold and exception policy. The result should control promotion according to that policy.
tb2: Inspector findings report vulnerability evidence, affected resources and severity that can inform release decisions.
tb3: Compare the supplied scan report with the stated severity threshold and documented exception policy to decide whether a finding is actionable.

Make the scan-policy check return failure for an actionable unexcepted finding and require its success before promotion; retain the report and policy decision as evidence.
tb4: Read the supplied Inspector report's affected resource, vulnerability evidence and severity. Compare findings with the stated threshold and documented exceptions. For an actionable unexcepted finding, make the supplied policy check return failure and require success before promotion. Retain the report and the policy decision. If a documented exception applies, record that policy basis rather than silently dropping the finding. This is a bounded release decision using supplied scan evidence, not a lesson in vulnerability exploitation, specialist remediation or inventing a new severity policy.

Compare an actionable unexcepted finding with one covered by a documented exception. Both remain scan evidence; the supplied policy determines their different gate outcomes. Retain the exception basis alongside the finding rather than claiming the scanner did not detect it. If a blocking policy result is tolerated by the workflow, the gate is not enforcing the stated precondition even though the scan ran.
tb5: A scan report alone is not an enforced release gate. The policy check must fail for actionable unexcepted findings and promotion must require its success. Also, severity should be read alongside the documented threshold and exception policy.
