tb1: An alarm should reflect a supplied sequence of metric samples, including gaps. To explain its state, separate the statistic and threshold from the size of the evaluation window and the number of breaches required within it.
tb2: A metric alarm evaluates a statistic over periods against a threshold and has OK, ALARM and INSUFFICIENT_DATA states.
tb3: EvaluationPeriods is the number of evaluated periods, and DatapointsToAlarm is the number of breaching datapoints required within that window.

Set the supplied metric, statistic, period, comparison operator and threshold along with the evaluation counts; compare the resulting state with the supplied samples.

Missing-data settings are breaching, notBreaching, ignore (retain current state), and missing (insufficient data when all datapoints are missing); missing is the default.

Before applying a missing-data setting, establish what CloudWatch retrieved. With the default sliding evaluation window, CloudWatch attempts to retrieve more datapoints than EvaluationPeriods. This evaluation range depends on the period and metric resolution. A wall clock evaluation window instead retrieves only the datapoints within its aligned window.

If the evaluation range contains at least EvaluationPeriods real datapoints, CloudWatch evaluates the most recent EvaluationPeriods real points, using older real points as needed. It ignores the missing-data setting in this case. If fewer real points are retrieved, CloudWatch includes all of them and fills only as many missing points as necessary using the configured treatment.
tb4: Suppose the approved samples for three evaluated periods are above, below and above the supplied threshold. Set EvaluationPeriods to 3 and DatapointsToAlarm to 2 for this example, alongside the supplied metric, statistic, period and comparison operator. There are two breaching datapoints in that window, matching the stated count requirement. Now examine the supplied missing-sample case with its selected missing-data policy. First check the retrieved evaluation range: if it supplies at least three real points, evaluate the most recent three real points and ignore the missing-data setting. Only when too few real points are retrieved should the configured treatment fill the minimum necessary gaps. Do not silently treat a gap as a real zero or a real breach. For the all-missing case, missing yields insufficient data; ignore retains the current state. Compare the resulting state with the supplied cases and retain the settings with the sample evidence.
tb5: EvaluationPeriods is not the number of breaches required. It is the number of evaluated periods; DatapointsToAlarm supplies the required breach count. Also, missing is the default missing-data setting, not a promise that every isolated gap immediately produces INSUFFICIENT_DATA.
tb6: Partially missing data has an important exception: CloudWatch can enter ALARM even with fewer real datapoints than DatapointsToAlarm if the oldest breaching datapoint in the evaluation range is at least as old as DatapointsToAlarm and every more recent datapoint is breaching or missing. In the source’s three-out-of-three example, EvaluationPeriods and DatapointsToAlarm are both 3, the treatment is missing, and the evaluation range has five points. Read these sequences from oldest to newest: “missing, missing, missing, missing, breach” does not immediately cause ALARM, but “missing, missing, breach, missing, missing” does. The second sequence has an older breach followed only by missing points; the first has only a new breach. Do not infer the state solely by counting the available real breaches.
