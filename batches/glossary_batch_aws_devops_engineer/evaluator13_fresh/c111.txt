tb1: A replacement plan can have a permitted order or be prevented by a lifecycle rule. These controls affect mechanics, but the operator still needs scope and impact approval for a permitted change.
tb2: By default Terraform destroys an object before creating its replacement; create_before_destroy requests the reverse order where supported.
tb3: prevent_destroy rejects a plan that would destroy the protected resource while that lifecycle rule remains in its configuration.

Set the supplied lifecycle argument in the resource block, introduce the controlled replacement-triggering change, and inspect the plan’s replacement order or prevention error before the approved permitted apply.

Lifecycle settings constrain replacement mechanics but do not replace scope and impact approval.
tb4: Set the supplied lifecycle argument in the resource block and introduce the approved controlled replacement-triggering change. Inspect the plan's replacement order or prevention error. By default Terraform destroys the old object before creating its replacement; create_before_destroy requests the reverse where supported. prevent_destroy rejects a destruction plan while that rule remains in configuration. If the plan is permitted, follow the supplied approval before applying it. Record the order or rejection evidence separately from scope/impact authorization. Do not describe a lifecycle setting as a substitute for review or as a guarantee that every replacement can be performed with both objects coexisting.

Compare two approved controlled plans: one requests create-before-destroy where supported, while another destruction is rejected by a still-present prevent_destroy rule. The first record concerns ordering; the second concerns plan prevention. Neither result proves the change's business impact is acceptable. Scope review and approval remain necessary for the permitted plan, while the prevention error is evidence that the configured lifecycle boundary blocked that destruction.
tb5: create_before_destroy is a request for reversed replacement order where supported, not a universal feasibility guarantee. prevent_destroy applies while its rule remains in configuration. Neither lifecycle setting replaces scope and impact approval.
