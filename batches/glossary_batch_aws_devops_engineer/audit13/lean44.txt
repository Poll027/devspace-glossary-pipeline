
### 44 aws.cloudformation_drift
INLINE out-of-band change=A live resource change made outside the configuration-management workflow.; supplied template=supplied
f1 CloudFormation drift detection compares supported explicitly declared resource properties with their current values.
f2 Run drift detection on the provisioned stack after the supplied out-of-band change, wait for completion and inspect the bucket’s expected and actual property values.
f3 Drift detection reports differences without repairing them; unsupported or undeclared properties may not be checked.
tb1 A stack's bucket property was changed outside CloudFormation in the controlled lab. Drift detection can show a declared-versus-current difference, but the operator must understand what it checked and what it did not do.
tb4 Run drift detection on the provisioned stack after the supplied out-of-band change and wait for completion. Locate the bucket's result and compare its expected and actual property values. Write the difference as a pair, such as supplied declared value A and current value B, rather than saying only drifted. Detection compares supported explicitly declared properties; unsupported or undeclared properties may not be checked. Keep that scope beside the result so a lack of reported drift is not described as exhaustive verification of every property. This task observes and records the difference. It does not repair the resource merely by running detection. A useful drift record names the stack resource, the specific checked property and its expected/actual pair. If another setting is not explicitly declared or supported for comparison, do not infer its correctness from this result. This lets the next operator see exactly what detection established. Running detection again without changing the resource does not perform the missing repair; detection and approved correction are different actions.
tb5 Drift detection reports differences without repairing them. It also does not promise to check every property: supported, explicitly declared properties are the comparison scope, and unsupported or undeclared properties may not be checked.

assessment distinguish_drift_detection_from_repair_and_exhaustive_verification

practice_anchor.success Provide evidence of the provisioned bucket and completed drift detection, identifying the stack resource, checked property, and expected/actual value pair. ### 45 aws.cloudformation_rollback
INLINE supplied CloudFormation template=supplied; supplied fault injection=supplied; stack events=CloudFormation records of resource execution status and failure reasons.; supplied fault scaffolding=supplied
f1 CloudFormation stack events record resource operation status and failure reasons during an update.
f2 After the supplied controlled update failure, inspect the first failing resource event and subsequent rollback events.
f3 UPDATE_ROLLBACK_COMPLETE indicates rollback to the previous working stack state; UPDATE_ROLLBACK_FAILED requires resolving the rollback failure before continuing.
tb1 A controlled stack update failed. The response needs both the original failure evidence and the rollback outcome; a final stack label alone can hide the sequence that explains the problem.
tb4 Inspect the supplied update's stack events, starting with the first failing resource event and its failure reason. Then follow subsequent rollback events. If the resulting status is UPDATE_ROLLBACK_COMPLETE, describe rollback to the previous working stack state. If it is UPDATE_ROLLBACK_FAILED, the rollback failure must be resolved before continuing. Retain the first failure and the rollback status separately in the record so that the update problem is not confused with a later rollback problem. Use the supplied controlled failure and approved response path rather than experimenting with new changes while the rollback outcome is unresolved. For an illustrative event sequence, suppose the update first reports a resource failure and later reports a rollback failure. The first event explains why the requested update did not complete; the later event explains why rollback did not complete. Preserve both reasons in their event order. Resolving only the first update problem does not justify ignoring the status that says rollback failure still needs resolution before continuing.
tb5 UPDATE_ROLLBACK_FAILED is not another success label for rollback. It requires resolving the rollback failure before continuing. Conversely, UPDATE_ROLLBACK_COMPLETE describes rollback to the prior working stack state, not successful deployment of the failed update.

assessment verify_rollback_to_previous_working_stack_state
assessment distinguish_completed_rollback_from_rollback_requiring_resolution

Apply the supplied controlled update-failure scaffolding, inspect the first failing resource event and its failure reason, and follow subsequent rollback events to determine the final stack state.
practice_anchor.success The supplied stack initially provisions one EC2 instance. After the controlled update failure, the learner records the first failing resource event and its reason separately from subsequent rollback events, and verifies that UPDATE_ROLLBACK_COMPLETE indicates return to the previous working stack state.
