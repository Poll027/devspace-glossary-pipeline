
### 104 recovery.credential_readiness
INLINE supplied backup and recovery resource checks=supplied; supplied recovery session and resources=supplied
f1 Recovery execution needs a valid, unexpired session with the permissions required for backup access and resource creation.
f2 Establish the approved recovery session, inspect its identity and expiry, and test the supplied backup-read and recovery-resource operations before rehearsal.
f3 A valid credential lifetime does not prove sufficient authorization; verify both access outcomes and lifetime.
tb1 Recovery rehearsal needs a valid session that can perform the required work. Check lifetime and authorization independently before using it for restoration.
tb4 Establish the approved recovery session and inspect its identity and expiry. Test the supplied backup-read and recovery-resource operations. Record both outcomes alongside the credential lifetime. If the credentials are unexpired but the backup-read test is denied, they are not ready for the required recovery. Conversely, permission evidence does not remove the need for a valid session during execution.
tb5 Unexpired credentials do not prove sufficient authorization. Recovery readiness needs both valid lifetime and successful required access tests for backup reading and resource creation.

assessment verify_backup_access_and_recovery_resource_creation
assessment distinguish_session_lifetime_from_authorization
practice_anchor.type tool_simulation
practice_anchor.objective Test one approved recovery session before rehearsal using the supplied identity, expiry, backup-read, and recovery-resource checks without exposing credentials.
practice_anchor.success The approved session is established, its identity and expiry are inspected, and both supplied operation outcomes are recorded alongside its lifetime. Readiness requires the expected identity, a valid unexpired session, and successful backup-read and recovery-resource operations; an unexpired session with a denied operation is identified as not ready.
visual_anchor.type UI_state
visual_anchor.purpose Show the approved recovery session's identity and expiry alongside the supplied backup-read and recovery-resource test outcomes, making lifetime and authorization separately visible without displaying credentials.
note Use approved session provider and safe supplied tests; do not expose credentials.

### 106 response.approval_stop
INLINE supplied remediation workflow=supplied; approval and stop controls=The remediation action executes only after approval and is blocked by an active stop condition.
f1 An aws:approve Automation step pauses execution pending approval or rejection by the designated approvers.
f2 Put the approval step before the protected operation and use the supplied branching or failure path to prevent that operation on rejection or stop.
f3 Stop an Automation execution with the approved stop operation when a stop condition occurs and inspect execution state before allowing further actions.
tb1 A protected Automation operation requires approval and an enforceable stop path. Position that decision before the operation and inspect the actual execution state when stopping.
tb4 Place the supplied aws:approve step before the protected action. Use the established branching or failure path so rejection or stop prevents that operation. In the supplied stop-condition test, use the approved stop operation and inspect execution state before allowing further actions. The approval step pauses for designated approvers; it is not authorization to run the protected action before they decide.
tb5 An approval request is not an approval outcome. Rejection or stop must prevent the protected operation, and a stop request still requires inspecting execution state before further action is allowed.
assessment verify_pending_or_rejected_approval_blocks_protected_operation
assessment verify_stopped_execution_blocks_protected_operation_before_further_actions
practice_anchor.type tool_simulation
practice_anchor.objective Add the supplied aws:approve gate before the protected operation in a bounded remediation workflow. Connect the supplied rejection or failure path, then use the approved stop operation when the supplied stop condition occurs.
practice_anchor.success The workflow pauses for designated approvers before the protected operation. Pending approval, rejection, and stop do not permit that operation. After requesting a stop, execution state is inspected before any further action is allowed.
visual_anchor.type UI_state
visual_anchor.purpose Make the approval step's position before the protected operation visible, together with pending, rejected, and stopped execution states and the protected operation remaining unexecuted in each case.
note Use supplied branching and stop operation; do not invent Automation document syntax.
