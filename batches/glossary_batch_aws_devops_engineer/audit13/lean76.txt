
### 76 security.audit_storage_encryption
INLINE KMS key-use authorization for SSE-KMS only, not SSE-S3=SSE-KMS reads require both S3 object access and permission to use the KMS key; SSE-S3 does not require KMS key-use authority. This local encryption model is taught here.; SSE-KMS key-use authority locally taught (not required for SSE-S3)=This concept teaches that SSE-KMS requires S3 object authorization and KMS key-use authority. SSE-S3 does not require KMS key-use authority.
f1 SSE-KMS encrypts S3 objects with an AWS KMS key, while SSE-S3 uses S3-managed keys.
f2 Reading an SSE-KMS object requires both s3:GetObject permission and kms:Decrypt authority for its key; SSE-S3 does not require KMS key-use permission.
f3 Configure the supplied KMS key as bucket default encryption and test reads with approved object/key authority and with KMS use denied; inspect the object’s encryption metadata.
tb1 An audit reader can address an S3 object but still lacks the required KMS authority. Separate object access, key authority and the individual object's encryption metadata before interpreting the read result.
tb4 Configure the supplied KMS key as the bucket's default encryption. For the supplied SSE-KMS object, test a read under approved s3:GetObject and kms:Decrypt authority. Then run the case where KMS use is denied and inspect the result. Read the object's encryption metadata to confirm what applies to that object. Changing bucket default encryption does not re-encrypt existing objects, so a default setting alone is not proof of an older object's encryption. Compare this with the stated SSE-S3 boundary: S3-managed-key encryption does not require KMS key-use permission. Keep those two encryption models distinct in the evidence instead of adding a KMS requirement to every S3 read.
tb5 Bucket default encryption does not change the individual encryption of objects that already exist. Inspect object metadata. Also, SSE-KMS read access needs both object permission and KMS Decrypt authority; SSE-S3 does not require KMS key-use permission.
tb6 Changing bucket default encryption does not re-encrypt objects that already exist; their individual encryption settings still matter.

### 79 automation.partial_failure
INLINE supplied mixed target results=supplied; per-target outcome=The success or failure recorded separately for each selected fleet member.; supplied mixed results=supplied
f1 A fleet command has separate invocation results for individual targets, which may differ within one command.
f2 Inspect invocation statuses and outputs and record successful, failed and unresolved targets separately.
f3 Use target-specific results to choose the scoped follow-up rather than blindly repeating the entire operation on already successful targets.
tb1 A fleet command may succeed on some targets and fail on others. Follow-up needs a target-by-target result map so that successful work is not blindly repeated.
tb4 For an illustrative three-target command, inspect each invocation status and output. If node A succeeded, node B failed and node C is unresolved, record those three categories with their target identities. Choose the supplied scoped follow-up using those individual outcomes. Do not label the unresolved node failed without evidence, and do not repeat the entire operation merely because one target failed. The separate invocation results are the basis for follow-up; a single overall command label cannot replace them. Keep the successful targets visible so the next operator can avoid treating the entire fleet as untouched. The follow-up record should retain what is known and what remains unresolved. For node A, successful output is evidence of completion; for node B, retain the failure evidence; for node C, keep the unresolved status until inspection establishes an outcome. This distinction prevents the next operator from treating uncertainty as permission to repeat a mutation on every target. Use only the supplied scoped follow-up.
tb5 Partial failure is not the same as total failure. Successful, failed and unresolved targets need separate records. Use those results for scoped follow-up rather than blindly repeating the operation on already successful targets.
