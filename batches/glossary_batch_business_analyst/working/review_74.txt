FACT f1 A context diagram represents the system as a single element with a boundary separating it from external entities.
FACT f2 Define the system’s purpose and boundary and identify its external actors and connected systems.
FACT f3 Draw the system centrally, place external entities around it, and use labeled directional arrows to show exchanges.
tb1 Imagine defining the boundary of an order service. A context diagram represents the system as a single central element, with external entities outside its boundary. The immediate question is what is inside this system and what exchanges information with it.
tb2 A context diagram represents the system as a single element with a boundary separating it from external entities.
tb3 Define the system’s purpose and boundary and identify its external actors and connected systems. Draw the system centrally, place external entities around it, and use labeled directional arrows to show exchanges.
tb4 For this hypothetical diagram, draw “Order service” centrally. Place “Dispatcher” and “External delivery service” around it as external entities. Label directional arrows with the exchanges: a dispatcher sends an order-selection request to the system; the system returns instructions; the system sends a dispatch request to the delivery service. These are example exchanges, not mandatory integrations.

Define the system’s purpose and boundary before placing the entities. Do not put the external delivery service inside merely because it communicates with the order service. The directional labels help the reader distinguish what flows into and out of the central system.

The useful output is a boundary-and-exchange view, not a detailed internal process. The central system stays one element here. That makes the context clear without introducing the internal tasks or screens that may implement it. Read the diagram back as purpose, boundary, external actors or connected systems, and labeled exchanges.
tb5 A context diagram does not expand the system into all its internal activities. It represents the system as one element and shows external entities and exchanges. A connected system is not automatically inside the boundary simply because there is an arrow to it.
