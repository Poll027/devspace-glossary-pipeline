tb1 Suppose Orders contains three hypothetical rows: North with Amount 40, North with Amount 60, and South with Amount 30. A stakeholder asks for total amount per branch, not the original order-level rows.
tb2 GROUP BY creates one result group for rows with the same grouping-column values.
tb3 SUM computes a total. Write SELECT group_column, SUM(value_column) FROM table_name GROUP BY group_column; for one total per group. In the ordinary grouping pattern, list each selected column outside aggregate functions in GROUP BY.
tb4 Write:
SELECT Branch, SUM(Amount) FROM Orders GROUP BY Branch;

GROUP BY gathers rows with the same Branch value into one result group. SUM computes the total within each group. North contributes 40 + 60 = 100, and South contributes 30. The result contents are therefore (North, 100) and (South, 30), with no output order promised by this query.

In the ordinary grouping pattern, each selected column outside an aggregate function belongs in GROUP BY. Branch is the unaggregated selected column here, while Amount is inside SUM. If the required question changes to totals per branch and service category, the grouping needs to reflect those selected grouping columns rather than pretending one branch total also identifies a single category.

The practical change is the level of the result: several source rows can contribute to one grouped total. Explain that to a stakeholder who expects to see individual orders. The query is not deleting those source details; its requested output is a group-level summary.
tb5 Selecting a group label and a total does not make every other source field meaningful at the group level. Follow the ordinary pattern of listing selected nonaggregate columns in GROUP BY. Also distinguish a per-group total from one original row’s amount.
